# M12 Wave 7 — Destruction / Retention Matrix

**Planning baseline:** primary `697048bb490e2b5e43c4427d520aa28e09d4dcde`.
**Runtime changes:** none. **Execution gate:** `M12_DESTRUCTIVE_RETENTION_ENABLED=false`.

This is a proposed authorization matrix, not approval to execute. `WAIT_*` means the action is ineligible until the named evidence is recorded. Customer WordPress content is not automatically part of account erasure. “Delete” means a possible future scoped action only after approval, provider evidence, and safe recovery checks.

| Data group / repository evidence | Possible Wave 7 disposition | Minimum planning semantics and blockers | Recovery / audit / provider caveat |

Require verified request, cooldown, current source version, Owner approval, legal/security approval. | Audit actor/action IDs, not secret values. Session IP/user-agent are personal data and follow approved log policy. Stable opaque subject ID may remain. |

## Cross-cutting constraints

1. No bulk cascade; enumerate dependent rows and explicit actions.
2. Prepare one subject-scoped immutable plan bound to request UUID, policy version(s), current source watermark, provider facts, exception decisions, and exact action list.
3. Recompute blockers and lock/revalidate the source immediately before each irreversible step.
4. Write and read back the independent tombstone before mutating erasable primary state; if journal is unavailable, fail closed.
5. Treat every provider object identity/version separately. Provider acknowledgment is not absence verification.
6. Retain failed/partial outcomes for reconciliation without retaining raw PII in general logs.
7. Zero-day is eligibility at trigger time, never execution.
8. Destructive action count remains zero until a separately approved implementation/activation phase.
