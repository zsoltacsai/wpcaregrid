## Public-route contract for a future marketing-only launch

This is the proposed acceptance contract, not a claim about deployed edge configuration.

| Request class | Required public behavior |
|---|---|
| Canonical host | Accept only the Owner-approved canonical `https://wpcaregrid.com`. If `www.wpcaregrid.com` remains an alias, issue only a same-origin/same-scheme canonical redirect to the apex; reject every other Host/authority. The actual DNS and ingress arrangement must first be inventoried. |
| Public `GET`/`HEAD` paths | Exact reviewed marketing paths: `/`, `/pricing`, `/en`, `/en/`, `/hu`, `/hu/`, `/en/pricing`, `/hu/pricing`; approved legal `/terms`, `/privacy`, `/cookie-policy`, `/dpa`, and `/legal/history/<uuid>`; `/robots.txt`, `/sitemap.xml`, listed favicon/touch icons; only content-hashed assets matching the current `/build/assets/<name>.(css|js|woff|woff2|ttf|svg|png|jpg|jpeg|webp)` policy. Verify every new public route before adding it. |
| Health | `GET/HEAD /up` may return only the source-defined generic bodyless 200 with `Cache-Control: no-store`; it must not reveal runtime, host, dependency or deployment details. Restrict it at the edge to monitor sources if the selected topology supports that without bypassing TLS/origin protections. |
| Every other path/method | Deny by default, before application/upstream dispatch. Specifically deny every method for login/password/activation/logout, account/customer/subscription, signup, checkout, Stripe/webhooks, billing, Owner, Operator, Connector, `/api`, backup/download, restore, scan, admin and unknown routes. Denials should be empty 404 (or edge 403/404), `no-store`, no redirect and no upstream dispatch. |
| Normalization and alternate routing | Treat raw and normalized paths as hostile: encoded and double-encoded slash/dot, semicolon parameters, duplicate slash, dot segment, trailing slash, case variation, method-override headers, `Forwarded`, `X-Forwarded-Host`, `X-Original-URL`, and host/SNI mismatch. Reject ambiguous forms; never normalize an unapproved route into an allowlisted route. Direct-origin requests must not bypass the same allowlist. |

The source gate is one application layer only. A production ingress/origin policy must independently enforce the method/path/host contract. The middleware recognizes the configured app host and its `www` alias; that does **not** establish DNS, TLS SNI, Nginx/default-vhost selection, CDN policy or origin isolation. If a CDN/reverse proxy is used, origin reachability must be restricted to it or protected by an independently verified origin control. If there is no CDN, prove the public reverse proxy is the sole route to the application. Do not put this application on the staging origin by assumption.

## Future authorized verification procedure

These are planned acceptance actions only; none was executed for this assessment. Before any probe or host command, Operations must identify the approved production environment, target and operator, and the Owner must approve the relevant read-only or release step. Use placeholders from that approved inventory; do not guess IPs or reuse staging addresses.

1. **Source/release identity:** re-read protected primary and active ruleset; pin candidate merge SHA and artifact digest; verify exact-SHA required CI and both MySQL concurrency gates; obtain Integration and independent AppSec exact-candidate decisions. Do not use a CI merge/test commit as a release SHA unless its tree and parents are proven to match the approved candidate.
2. **Sanitized inventory:** record environment identifier, provider/OS, host separation, DNS A/AAAA/CNAME, CDN/edge/origin, listeners/vhosts/SNI/default-server behavior, FPM pools/socket/worker identity, database and queues, storage, process identities, deployment/controller paths, logging/monitoring and rollback artifacts. 3. **Route policy test in an isolated release harness:** enumerate all exact public GET/HEAD paths and assets; test every sensitive prefix and unknown route under GET/HEAD and method variants. Assert denied responses are empty 404/403, no Location, no-store, and no application upstream/controller dispatch. Test POST/write route denials only where the harness proves the request cannot reach production application logic.
4. **Authorized, low-risk external smoke after separate Owner GO:** DNS queries for canonical and approved alias; TLS verification with SNI and certificate-chain validation; single GET/HEAD to allowlisted pages and generic `/up`; verify exact redirect, status, headers, noindex/indexing decision and no sensitive body. Verify direct-origin denial only after origin addresses and approved test path are independently provided.
5. **TLS and operations:** inspect effective certificate SAN/issuer/expiry and renewal timer; perform renewal dry-run only with separate operational approval. 6. **Runtime/cutover rehearsal:** in an isolated environment, build/boot the exact release with the selected runtime, run `composer check-platform-reqs --no-dev --lock` (without ignore flags), app system checks and HTTP smoke. Demonstrate PHP 8.4 rollback to an exact known-good artifact with no DB rollback assumption. Never alter production PHP or staging as part of this assessment.
7. **Receipts and stop conditions:** store before/after release SHA, artifact hash, environment ID, change/approval IDs, check links, health/route/alert results, runtime identity, rollback SHA and sanitized operator/time metadata in the protected release receipt. Stop and retain the previous safe page/gate for any ambiguous target, unexpected listener, route dispatch, runtime mismatch, alert failure, missing approval or evidence conflict.

## Prioritized launch blockers

1. **Production target and ingress are not evidenced.** Identify actual production host/edge and prove no direct-origin or alternate-vhost path reaches staging or an unrestricted Laravel backend.
2. **Effective production allowlist is not evidenced.** Implement and independently verify exact GET/HEAD host/path policy at both edge and origin; explicitly deny sensitive paths, non-GET/HEAD methods, and unrecognized normalization/host forms.
3. **TLS and safe public hostname behavior are not currently verified.** Prove certificate, redirect, renewal and carefully scoped HSTS for the actual production ingress.
4. **No production Laravel release identity or receipt exists.** Identify a protected controller, artifact provenance, exact SHA/CI gate, immutable receipt and production-equivalent rollback rehearsal.
5. **Production runtime and isolation are unknown.** Record PHP/FPM/user/socket/extensions/OPcache plus app key, DB, queue, cache, session and storage separation; keep PHP cutovers separate.
6. **Operational detection is not evidenced.** Configure and test logs, alert delivery, on-call/escalation, health probes, TLS/DNS/deployment/resource monitoring.
7. **Legal/privacy and publishable content lack current acceptance evidence.** Obtain qualified review, language/effective-date approval, cookie/analytics disposition and explicit indexing decision.
8. **Independent release-specific AppSec acceptance is pending.** Review the actual deployed edge/origin and exact release, not only merged middleware code or CI.
9. **Staging PHP 8.5 transition remains separately blocked.** Close the integration bootstrap/producer-consumer contract, review its implementation and obtain the staged approvals; do not treat the CI FPM lane as cutover.
10. **Paid beta requires a separate operational/legal/accounting gate.** Validate Stripe, invoicing/tax, privacy/offboarding, supported host scope and isolated platform DR before inviting or charging anyone.
