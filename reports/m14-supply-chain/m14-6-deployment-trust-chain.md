# Staging Deployment Trust Chain

Audited source: `scripts/deploy-staging.sh`, `scripts/run-scheduler.sh`, `docs/DEPLOYMENT.md`, current staging host over strict SSH. This is not a production review or change.

## Observed chain

1. Human runs `bash scripts/deploy-staging.sh <full SHA>` as `deploy` from `/var/www/wpcaregrid`; script path is the currently checked-out trusted baseline. There is no GitHub Actions deployment job.
2. Script requires deploy identity, exact app directory, fixed origin `git@github.com-wpcaregrid:zsoltacsai/wpcaregrid.git`, `.env` ownership/mode 0600, clean checkout, existing healthy staging state and expected staging environment.
3. The current host script locks deployment; captures immutable baseline; fetches only the fixed authoritative branch; accepts a full commit SHA that is an ancestor of fetched tip. **Candidate PR #115** changes forward mode to require `target == fetched branch tip` and invokes the token-free release verifier from the protected controller directory before creating a backup or changing any gate. This co-location is required for the first rollout because the current application checkout may predate the verifier. The verifier runs with a clean environment, requires a completed successful push run on the exact SHA, all seven stable job names and the MySQL process/concurrency step. A separate `--rollback SHA` mode requires an administrator-installed root-owned one-SHA approval file, requires the rollback SHA to be an ancestor of the current baseline and branch, and still requires exact-SHA successful CI. No later pull/branch checkout substitutes the validated SHA.
4. Creates a mode-0600 gzip-verified DB dump in `deploy`-owned mode-0700 directory; coordinates scheduler lock/pause, Nginx gate and named queue workers before source switch.
5. Checks out exact target, runs Composer production install, npm clean install/build, migrations, caches and Connector build/verification; checks exact HEAD, working tree, PHP-FPM readability, workers, scheduler, health and HTTP security smoke.
6. On safe pre-migration failure it can restore pinned baseline code/dependencies/assets; after migration attempt it does not automatically rollback data and deliberately keeps service gated if recovery is unproven. No automated database restore.

## Containment deployment attempt and recovery

The root-owned reviewed controller from merge `854a26832d864146fc493e75225cf6438ed932b9` was invoked against the clean baseline only after narrow sudo was verified. It passed initial checks, created a private pre-deploy DB backup, guarded scheduler/Nginx, and stopped both named workers. It then aborted before git checkout because installed helper v1 treated Supervisor's nonzero status for a valid `STOPPED` state as an operation failure (M146-F10). PR #107 merged the parser fix in application/helper source at `dfaa2a9e4209cea310ef2241e58b1fe84e30c3e8`; exact-head CI `39031728761` and merged-primary CI `39032648566` passed. The installed root helper is still v1 until separate admin installation. Controller recovery left the gate closed; recovery used only helper `worker start-all`, `scheduler-resume` and `gate-off`. Post-recovery: HEAD remains `3debba99c677b68465cf439733f440442fbd0f22`, tree clean, both workers RUNNING, scheduler resumed, no gate/pause markers, `/up=200`, and `php artisan system:check` passed deploy-critical parts. The baseline was restored without code switch or target-controlled install.

## Target-code timing and trust-controller finding

The running deployment shell is loaded from a protected root-owned controller before target switch; target source does not replace that running shell. The controller installs only the exact hash-pinned `scripts/run-scheduler.sh` through the fixed helper, then executes target Composer (including allowed scripts), npm build, Artisan migrations/cache commands and Connector packaging as deploy. The active sudo policy no longer grants arbitrary root commands to that user. The M146-F10 source fix is merged, but the host must install the reviewed helper revision through its separate root/admin path before a target-code deployment can use it.

The prior exact-SHA/ancestry checks established commit identity and branch ancestry, not that the SHA was merged through an approved PR or had green checks. F01 is closed by effective branch ruleset `25300175` and seven exact required checks. PR #115 implemented forward tip equality and exact post-merge push CI verification. Its token-free API approach passed local checks and exact merged-primary CI (`39037273263`); PR #118 exact merged-primary run `39051589381` passed all seven mandatory checks on the target subsequently reported deployed to staging. The owner-reported staging receipt records that exact target and runtime HEAD. The final staging validation evidence is attributed in the closure report.

## Future release protocol

- Require reviewed PR, all seven PR-head checks, merge to authoritative branch, then successful exact SHA CI on the merged-primary push. The candidate token-free verifier reads the public Actions run/jobs endpoints and validates run event, branch, workflow path, conclusions, all seven checks, and the embedded concurrency step.
- Forward deploy only if the supplied SHA is the fetched authoritative tip. Rollback is a separate `--rollback SHA` path restricted to a root-owned administrator-approved SHA, ancestor of current baseline and fetched branch, with its own exact-SHA green CI evidence. No rollback approval file exists by default.
- Run target-controlled build/migration steps without root. Replace broad sudo with a small root-owned helper taking enumerated fixed actions and validated literals; do not allow shell strings, arbitrary paths, or target-controlled command names.
- Preserve strict client→staging and staging→GitHub host-key checks. Track key/fingerprint scope and rotation through reviewed admin evidence; no blind host-key acceptance.
- The candidate private machine-readable receipt records requested SHA, actual HEAD, baseline SHA, mode, CI run ID, UTC time, lockfile hashes, PHP/Composer/Node versions, migration status, Connector version/source and ZIP SHA-256, build manifest hash and health result. It stores no `.env`, token or credential values. It is deploy-owned and therefore evidence, not a trust root.
- Keep current in-place build-on-staging approach for now: it avoids CI artifact substitution and preserves exact source deploy, but it executes builds on a privileged host. After sudo isolation, this is acceptable for staging; do not shift to CI artifacts without provenance verification, source SHA binding, checksum validation, rollback and storage policy.

Future fault matrix is in `m14-6-fault-injection-plan.md`. Staging-only; no production test or customer mutation.
