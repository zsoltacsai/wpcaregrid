# M10 monitoring risk register

| Risk | Impact | Mitigation | Regression evidence |
|---|---|---|---|
| SSRF through stored website URL, redirects, DNS rebinding | Probe reaches database, metadata service or private tenant network | Server-owned canonical host; public-IP validation at resolution and connect time; no arbitrary target API; redirect limit/revalidation; egress deny private/reserved ranges; strict schemes/ports | Unit IP-range matrix, fake DNS rebinding, redirect-to-private, IPv6 mapped/local cases, egress integration test |
| One compromised tenant causes probe abuse or alert flood | Resource exhaustion and cross-tenant leakage | Per-tenant/host quotas, concurrency cap, jitter, target ownership/website binding, response size/time limits, circuit breaker | Flood/parallel tests, tenant isolation feature tests |
| False outage due to monitor VPS DNS/egress/provider failure | Many sites alerted incorrectly | Separate probe failure from target failure; correlate local resolver/egress health; require confirmation and independent result when available; external monitor/dead-man outside same host | Shared-failure simulation and external endpoint blackhole test |
| Site-health signals race/stale Connector reports show false green | Missed incident or premature recovery | Freshness deadlines, source timestamps, 2-success recovery, preserve Connector Presence rules; stale is unknown | Clock/freshness boundary tests and delayed heartbeat tests |
| Alert storm/flapping | Owner/operator mail overload | Candidate states, consecutive thresholds, stable incident key, one outbox event/transition, cooldown, flapping suppression and shared-provider incident correlation | Simulated 3/30m flaps, thousands of repeated failures, duplicate worker test |
| Alert delivery succeeds but DB update fails or vice versa | Duplicate/missing delivery | Transactional outbox + unique delivery key + provider idempotency where available; at-least-once retry but deduped | Crash between send and mark-sent; duplicate delivery concurrency test |
| Monitoring tables grow without bounds | DB pressure/backup size increase | Latest-result upsert, transitions only on changes, bounded evidence, 7-day raw data, 90-day online transitions/delivery, purge closed historical rows by batch | High-volume retention test, open incident retained under purge |
| Monitoring consumes same DB/queue already degraded | Monitor self-observation unavailable during outage | External dead-man endpoint/independent channel; reserve bounded queue capacity; endpoint `/up` stays cheap; no dependence on failing queue for basic external check | Pause DB/queue and verify external observer detects absence |
| Confusing configured/reachable/verified states | False assurance for S3, mail, Stripe | Distinct enums and timestamps; read-only probes; never call config presence “healthy” | UI and adapter tests for configured-only/old probe/failure |
| Sensitive telemetry leaks into alerts/logs | Credentials, customer data, exploit details disclosed | Typed evidence allowlist, host-only identifiers, bounded strings, redact URL/query/headers, no response bodies, access control | Secret-pattern scan, malicious payload redaction tests, Owner/Operator authorization tests |
| Provider-wide outage becomes N site incidents | Noise and operator confusion | Correlation key for provider/network and individual affected checks; group presentation without hiding child evidence | Multi-site S3/DNS failure test |
| Maintenance hides real outage indefinitely | Blind period | End-bounded windows, maximum duration, audit, monitor continues, hard expiry, visible suppression, critical bypass rules | Expiry and overlong-window tests |
| MySQL uniqueness semantics differ from SQLite | Duplicate open incidents/outbox under concurrency | MySQL is authoritative for atomic claim/unique race tests; SQLite tests only functional behavior | Separate-process MySQL concurrency CI gate |
| Health aggregate becomes incompatible with current product semantics | Regressed Site Health/customer display | No numeric score; retain current rank/unknown contract; introduce new dimensions behind tests and versioned source IDs | Existing SiteHealth tests plus snapshots for old dimensions |
| External probe rate or provider costs exceed expectation | Provider bill or customer-host impact | Conservative cadence, jitter, request/byte caps, gradual rollout, per-plan policy only if approved, load test to 10k model | Rate/cap tests and staged synthetic fleet benchmark |
| Independent monitoring choice remains open | SaaS total outage may be invisible | Mark as recommended public launch gate; choose external provider/cost and independent notification destination before claiming end-to-end self-monitoring | Owner records service, owner account, access/rotation and outage-drill evidence |
| Customer notifications sent without policy | Legal/product trust issue | Owner+Operator only by default; customer email disabled until explicit approved policy and template | Assert no customer recipient in default policy and test feature flag default-off |
| Security incident duplicated into generic incident pipeline | Inconsistent acknowledgement/remediation state | Reference SecurityIncident ID and derive display signal; do not clone its lifecycle or change remediation | Security workflow contract tests |
| Provider check is active side effect | Charges, payment mutation, real mail, DNS/backup write | Read-only probe contracts; no Stripe charge, test mail, provider write/delete, DNS mutation, or customer WebsiteJob | Mock command allowlist; integration tests assert no mutation API calls |

## Adversarial review result

The largest architecture flaw would be equating a healthy local `system:check` with public SaaS availability. The plan explicitly separates local component observations from an independent dead-man monitor. Another dangerous flaw would be saving every HTTP response/exception or using a user-editable URL; both are prohibited. Main source of truth remains subsystem-specific: backup verification is decided by the backup engine, security state by SecurityPosture/incident records, Connector state by Presence, and M10 provides freshness, incidents and delivery around those facts.
