# GO-13 Workstream B — PHP-FPM confinement (AppArmor + systemd), version 1.0.3

Status: **source preparation only.** This document and `deploy/php-fpm-confinement/1.0.3/` do not authorize any host change. Nothing is loaded, installed, restarted or reloaded by the repository, and no active service, profile, drop-in, Nginx file or helper is altered by this change. Every host step below needs its own exact-scope Owner GO after merge, independent QA and AppSec review, and a fresh read-only inventory. Packages are immutable: 1.0.0, 1.0.1 and 1.0.2 were never installed and their bytes are frozen. the tests pin each frozen directory's **Git tree object id** (it commits to every file name, mode and blob id), re-derive it from the historical commit when history is available, reject any uncommitted or untracked change, and prove the id is reproducible from the bytes alone. 1.0.2 (which let the deploy CLI connect to any IPv4 TCP address) is superseded by 1.0.3; changed bytes always ship as a new version directory.

## Why this exists

Production and the existing staging pools run PHP-FPM as the **same UID/GID, `www-data` (33)**. File mode and ownership therefore cannot keep one environment out of the other's files. The deploy tooling already makes shared secrets group-readable by that GID (`shared/.env` mode `0640`, `shared/storage` mode `2770`, see `scripts/deployment_backend_v2.py`), so any `www-data` process that can open a path can read it. Confinement has to come from the kernel LSM and the service's mount namespace, selected per systemd unit.

**No new users, groups or FPM UID** are introduced. That is a hard requirement of GO-13.

## The invariant that orders every stage

> **Invariant I.** Production group-readable secrets must not exist, and no production traffic route may be opened, until **every same-UID (`www-data`) peer is enforce-attached to a confinement profile and live-accepted**. Rollback must fence production first so the invariant still holds after any peer is restored to unconfined.

"Peer" means every process that can read a group-33 `0640` secret file, that is **any real, effective, saved or filesystem UID 33, any GID 33, or supplementary group 33** (a deploy shell in the `www-data` group qualifies), plus every member of every service cgroup, root-owned masters included. `acceptance/collect-peers.py` enumerates all of them in two consecutive stable scans and the verifier maps **every one to exactly one explicitly permitted class; an unknown process blocks.** The canonical source-policy contract (owned by workstream A, see Contract binding) applies the same rule. The classes are:

| Class | Why it holds uid/gid 33 | Permitted state |
| --- | --- | --- |
| FPM pools: `production`, `staging-next`, `staging-legacy` | FastCGI workers and their (root) masters | label `<its profile> (enforce)`, in its own unit |
| `nginx` | edge workers and master | label `wpcaregrid-nginx (enforce)`, unit `nginx.service`; reads only public web roots and the three FastCGI sockets, denies both environments' `.env`, config caches, code and storage |
| `jobs-supervisor`, `jobs-scheduler`, `jobs-legacy-scheduler` | Supervisor queue workers and their master; the staging-next and legacy staging scheduler services | label `wpcaregrid-php-cli-staging (enforce)`, units `supervisor.service` / `wpcaregrid-staging-next-scheduler.service` / `wpcaregrid-staging-legacy-scheduler.service`; staging only, production denied |
| production queue workers and scheduler | not needed (marketing-only production) | **fenced**: scheduler `.timer`/`.service` units `masked` and `inactive`, no active or autostarting `wpcaregrid-production-*` Supervisor program, both fence markers present; and, if one were ever started, the job profile still denies every production path |
| **production deploy CLI** (transient) | the production root-console helper's `php8.4` runs (`runuser --user www-data --group www-data -- /usr/bin/aa-exec -p wpcaregrid-php-cli-production-deploy -- /usr/bin/php8.4 ...`): runtime identity probe, `package:discover`, `config:cache`, and the Phase B runner once moved to `/usr/bin/php8.4` | label `wpcaregrid-php-cli-production-deploy (enforce)`, exe and argv0 `/usr/bin/php8.4`, all uids **and gids** 33 with no supplementary group, **cgroup exactly the root-console session scope `/user.slice/user-0.slice/session-N.scope`, never a `*.service` unit**, a command-line hash (the exact allowlist of the helper's fixed commands is enforced by workstream A's contract), no descriptor into staging or the control plane, **age under 960 s** (a daemonised `php -S` or `queue:work` is not short-lived); none may exist in the pre-production phase or during rollback |
| trusted operator identities holding gid/supplementary group 33 unconfined | deploy and administration shells | **none by default** (`permitted_group33_holders` is empty): a reviewed decision, never a default |

**There is no `cron`/`sh` class.** A pinned crontab does not confine an unconfined same-UID shell that holds or opens production secrets, and no exec-path attachment can reach the `CRON` and `sh` processes themselves. `www-data` cron and `at` jobs are therefore not permitted at all: any www-data crontab, `/etc/cron.d` entry running as `www-data`, `at` job, or process under `cron.service` holding uid/gid 33 blocks production. The legacy staging scheduler runs from `wpcaregrid-staging-legacy-scheduler.service` instead.

`ACCEPTED_UNCONFINED_SAME_UID_COMM` is empty and stays empty.

## Layers and what each one is for

1. **AppArmor profile per unit** (`AppArmorProfile=`, no attachment path). Path rules apply to the *resolved* path, so a symlink does not widen access. This separates the shared-UID pools.
2. **Mount namespace per unit** (`InaccessiblePaths=-…`, `ProtectSystem=strict` + `ReadWritePaths=`, `ProtectHome=yes`, `PrivateTmp=yes`). Independent of AppArmor; checked separately from it.
3. **Process visibility and tracing**: `audit deny ptrace,` in every profile (also gates cross-process reads of `/proc/<pid>/{environ,mem,maps,fd,…}` and `process_vm_readv`), explicit denies for `cmdline`/`environ`/`fd`/`root`/`exe`, `ProtectProc=invisible`, `ProcSubset=pid`. `ProtectProc=invisible` hides only **other-UID** processes; every pool is `www-data`, so it adds nothing between pools and is not relied on for that. systemd 255 on Ubuntu 24.04 has no `PrivatePIDs`; on systemd 256 or newer it is a stronger replacement and would be a new artifact version.
4. **Abstract unix sockets** are denied (connect/send/receive/bind/listen/accept) because path rules and `InaccessiblePaths=` cannot see them and systemd has no per-unit switch short of a private network namespace, which the database connection forbids.
5. **FPM pool hygiene** (production): own socket, `clear_env`, no `env[]`, no TCP listener.

## What the source tests prove, and what they do not

Tests: `python3 scripts/tests/php-fpm-confinement-test.py` (isolated; no host access, no profile loading; real symlinks only inside temporary directories; the fixture tool runs in a temporary root).

Proven by source tests:

- Exact file set and `SHA256SUMS`; `binding.json` agrees with the matrix and the files, so the canonical contract can bind the package mechanically.
- An AppArmor path-rule model evaluates `acceptance/matrix.json` against each profile **in both directions** (secrets, config, storage, code, state, backups, control plane, sockets, exec). Deny beats allow; unlisted paths default to deny. Symlink escapes (absolute, relative, chained) are denied on the resolved path.
- `ptrace`, `/proc`, capability, mount, `dbus`, raw-socket, abstract-socket and signal rules exist in every profile; signals cannot cross pools.
- A guard compares each matrix check under the **original** profile and the **derived probe** profile: any check the two answer differently (the probe profile grants python exec) must carry `probe_scope: original_profile`, so a probe-only grant can never masquerade as a tested denial (`exec-python` is tested against the original profile, see acceptance step 7).
- The acceptance tooling itself: the probe emits exactly the result ids the verifier requires; the verifier refuses on any mutation (errno without audit, wrong audit profile/pid/operation/target, masked baseline, confined success, unconfined or missing same-UID peers, incomplete inventory, pid reuse, foreign descriptors, uncalibrated ptrace, descriptor-transfer bypass, unexplained denials); the fixture tool refuses real data and never deletes changed files; the collector is read-only and fails closed on unreadable processes.
- Unit and drop-in directives are an exact reviewed set; no `+`/`!`/`-` exec prefix, no `ConditionSecurity`, no `OpenFile`/`Sockets`/`BindPaths`, `FileDescriptorStoreMax=0`, `StandardInput=null`.
- Mutation tests: widening an allow, removing a deny, adding `ptrace`, bare `signal`, raw network, exec/write/link grants, capabilities, an unparseable rule, an unreviewed include, `User=root`, a fail-open `AppArmorProfile=-…`, and pool/unit/matrix edits each produce a finding.
- If `apparmor_parser` exists it compiles every profile and every derived probe profile (`-Q -K`, no kernel load, no cache). CI requires it (`PHP_FPM_CONFINEMENT_REQUIRE_PARSER=1`); a local run without it proves nothing about syntax.

**NOT PROVEN by source tests.** Source tests cannot prove kernel enforcement. The model is not the kernel, and the verifier tests run on synthetic evidence. Unproven until the live acceptance below passes on the host:

- That the host kernel enforces AppArmor `ptrace`, `signal`, `unix` (including abstract addresses and `file_receive`) and file mediation for these profiles, and writes the audit records the verifier requires. Record formats are matched generically and have not been observed on a real kernel.
- The content of the external abstractions (`base`, `nameservice`, `ssl_certs`).
- What happens to descriptors inherited across `execve` (see Inherited descriptors).
- Mount-namespace behavior on the host.
- That FPM and the packaged helpers run under these profiles.
- Anything about TCP ports: **AppArmor 1.0.3 does not separate TCP ports.** All pools except the deploy CLI (which has no TCP) can reach `127.0.0.1` database ports; separation rests on distinct database credentials and users.

The artifacts fail closed: an unloaded profile makes systemd refuse to start the service, unknown access is denied, the probe refuses unless it runs in the expected label, and the verifier refuses unless baseline, audit and peer enumeration all agree.

## Observation schema this package's tools produce

`collect-peers.py` emits `{schema: 2, complete, reasons, incomplete_reasons, matrix_sha256, boot_id, collected_start_ns, collected_end_ns, scans (>= 2), processes: [{pid, ppid, state, uids[4], gids[4], groups, comm, argv0, cmdline_sha256, starttime, label, unit, cgroup, exe, fds}], units: {unit: {present, pids}}, production_surface: {roots_present, real_files, fixture_files}}`. It includes every process with any uid/gid/supplementary group 33 and every member of a known service cgroup; it is only `complete` when two consecutive scans agree on `(pid, starttime, label, unit, uids, gids, groups)`, cgroup membership matches each process's own cgroup file, the boot id is unchanged and nothing was unreadable. The verifier (`verify-acceptance.py`) maps every process to a class (label + unit) or blocks. Production job fencing and the www-data cron/at state are observed by workstream A's collector, not here; this package only states the required values (`binding.json` rules).

## Known conflicts and limitations (surface before any GO)

1. **Non-FPM peers are classes, not gaps.** nginx, Supervisor queue workers, and the staging-next and legacy staging scheduler services each have a profile bound by unit; production's jobs are fenced. What remains unproven is host reality: the packaged `nginx.service`/`supervisor.service` helper commands, the job dispatcher/launcher paths (`/usr/local/bin/wpcaregrid-php`, `/usr/local/bin/wpcaregrid-scheduler`, any launcher under `/usr/local/` or `/home/deploy/.private/`), the legacy scheduler service (it does not exist yet: it replaces the www-data cron entry and must be created and reviewed before Stage 3) and sibling vhost roots outside `/var/www/*/public` are assumptions that complain-mode soak must confirm; anything unlisted fails closed.
   - *Migration prerequisite.* The legacy `www-data` crontab must be retired (and any `at` job removed) before the peer gate can pass. This is a real change to legacy staging operation and is its own Owner GO; until then Stage 4 fails by design.
   - *Production jobs never run.* Masking the scheduler units is the fail-closed start policy: a masked unit cannot be started by anything. A future need for production jobs is a new artifact version with its own profile and a new Owner decision; it must not be unmasked ad hoc.
1a. **The deploy CLI has no TCP; it has one unix socket, by Owner decision.** The code that runs under it reads production `.env`, and AppArmor cannot restrict a TCP destination, so any inet/inet6 right (the 1.0.2 rule allowed every IPv4 TCP address) would be a direct exfiltration path and is gone. The helper's runtime identity probe must reach the production MySQL instance, so the profile allows one thing: connecting a unix STREAM socket to the pathname `/run/mysqld/wpcaregrid-production.sock` (the production instance in `scripts/production_g1_mysql_contract.py`; the isolated restore instance has a different socket and is denied). The path is fixed in the profile and in `binding.json`; there is no environment-controlled path, no `${}` variable and no TCP fallback, and the probe must set `unix_socket` to exactly that path (no host/port). **Source has not checked the live host:** if mysqld's socket is elsewhere the probe is refused and acceptance fails closed (the `socket:mysql-production` allow check fails); the helper must verify the observed mysqld socket (path, socket type, owned by the production instance) equals the binding and keep the exact server-UUID check. `package:discover` and `config:cache` need no socket at all. **Phase B stays disabled and is not authorized here:** AppArmor cannot tell a query from DDL on an allowed socket, and code under this profile can use the `.env` credentials over it exactly as the FPM pool can, so keeping Phase B off is helper policy, not something this profile enforces. If a command is ever shown to need anything more (TCP, another socket), that is a new Owner decision and a new package. The PHP extension and ini set and whether Laravel needs a temp directory (none is granted) are assumptions confirmed in complain mode; anything unlisted fails closed. The profile also runs as `www-data` and can read `.env`: it is covered by the same R2 fence and the post-activation peer gate. The live probe's `net:*` and `socket:*` checks prove this on the host: socket creation for IPv4, IPv6, datagram, unix datagram and netlink, `bind`, and an actual loopback TCP connect over IPv4 and IPv6 to the harness sender's listeners must each be refused with their own audit event after the unconfined baseline connected; the exact MySQL socket must connect; the restore instance's socket, the vendor `mysqld.sock` and every FPM socket must be refused. A kernel that does not mediate network access makes the acceptance fail closed instead of passing.
1c. **Residuals of the deploy CLI profile, accepted and stated.** (i) The MySQL socket is a data channel: `.env` credentials give full SQL on the production instance (the same as the FPM pool), so the database grant of the application user must have **no FILE, REPLICATION or SUPER privilege**, `secure_file_priv` set and `local_infile` off, and a dedicated least-privilege identity for the probe is worth considering (workstream A). (ii) An inherited stream descriptor from the root console (an ssh agent, a control socket, journald stderr) is not tied to the MySQL peer, because this parser rejects a pathname peer address; the helper must start the CLI with **no inherited sockets** and `close_fds`. Journald stdout streams and `/dev/log` are denied in the profile. (iii) The write grants cover every release's `bootstrap/cache`, including the live release FPM includes, and shared storage `logs` and `framework/{cache,views}` (not the rest of storage): code that runs here can plant cached PHP that FPM, which has network access, later executes; this is the inherent limit of a no-network claim, covered by the helper's sealing of the cache (workstream A) and the R2 fence. (iv) The child's stdout and stderr go to the helper and are not confinable: the helper must not store them where staging can read them. (v) `rw` on the socket also permits unlink and rename; verify on the host that `/run/mysqld` is not group-writable by gid 33 (workstream A's pre-probe check covers it). (vi) The `socket:mysql-production` allow check needs the host's real socket: if it is elsewhere acceptance fails closed.
1b. **`bootstrap/cache` is www-data-owned inside a root-owned release.** The helper pre-chowns the candidate release's `bootstrap/cache` to `33:33`, so `www-data` code can plant symlinks or replace `config.php` there; this profile can write the cache of any release, including the live one FPM includes. Requirements on the helper (workstream A): root-side steps on that directory (`chown -R`, copy, remove, rsync, tar) must not follow symlinks, run with `umask 077`, and re-verify owner, mode and absence of symlinks before `current` is switched; the fence (R2) never follows symlinks.
2. **The legacy overlay is weaker by design.** `php8.4-fpm.service` serves legacy staging and sibling vhosts whose paths are not enumerated in this repository, so it keeps its existing access and only gains denials. A real allowlist needs the sibling inventory first.
3. **`/run/php` is one shared directory.** AppArmor denies the production profile access to other sockets; the systemd layer cannot.
4. **Signals from unconfined `www-data` processes** (systemd itself) are accepted so stop/reload works; availability, not secrecy, is affected.
5. **PHP 8.4 only for production, PHP 8.5 only for staging-next.** A different version is a new artifact version.
6. **The packaged `php8.5-fpm.service` is not in the repository.** The profile grants `php-fpm-socket-helper` and `dash` only. If the host unit runs other helpers (for example `update-alternatives`), enforce mode fails closed and the service does not start. Record `systemctl cat php8.5-fpm.service` first; do not widen the profile without reviewed complain-mode evidence.
7. `ProcSubset=pid` and the `/proc` denies may be stricter than PHP needs; treat a new denial as a stop, not a reason to loosen rules.
8. **Some matrix checks are model-only** (`live: false`): root-owned write targets that DAC and read-only mounts also refuse, `/root`, pid-1 `/proc` entries and the like cannot show an AppArmor-specific denial, and are never presented as live evidence. Control-plane/home/shadow/MySQL fixtures are `optional`: if the real parent directory is not traversable by `www-data`, the check is reported **UNPROVEN**, never PASS, and confined success there still fails.
9. **Real staging paths are opened, never read.** Deny targets in the live staging trees use the real files (only `open()`); only exactly-canary-sized fixture files are ever read.

## Installation and staged cutover (each numbered stage needs its own Owner GO)

Order is dictated by Invariant I: **both staging peers are confined and live-accepted before production secrets or a production route can exist.** Run only as the approved root console from a verified copy of the package:

```bash
cd "$PKG"            # root:root 0700 copy of deploy/php-fpm-confinement/1.0.3 from the reviewed SHA
sha256sum -c --strict SHA256SUMS
```

**Stage 0 — verify and stage the package (no unit search path, no AppArmor path, no load).** Copy the verified package to `/usr/local/libexec/wpcaregrid-php-fpm-confinement/1.0.3/` (`root:root 0700`), which is neither a systemd unit/drop-in search path nor an AppArmor profile directory. Stage 0 does not install any profile, unit, drop-in, FPM config or fixture, and does not run `daemon-reload`. Because that directory is root-only, `www-data` cannot execute anything from it, so the one non-secret harness file the acceptance runs as `www-data` needs is published separately: `install -d -o root -g root -m 0755 /usr/local/libexec/wpcaregrid-php-fpm-harness/1.0.3` and `install -o root -g root -m 0644 "$PKG/acceptance/fd-sender.py" /usr/local/libexec/wpcaregrid-php-fpm-harness/1.0.3/fd-sender.py`, then verify the published copy against the package pin (`grep ' acceptance/fd-sender.py$' "$PKG/SHA256SUMS" | sed 's# acceptance/fd-sender.py# /usr/local/libexec/wpcaregrid-php-fpm-harness/1.0.3/fd-sender.py#' | sha256sum -c --strict -`). It is stdlib-only, refuses to run as root, serves only the exact fixture canary, and contains no secret; that directory is not a unit or AppArmor search path. Record the Preconditions inventory. Nothing about any service changes.

**Stage 1 — staging-legacy overlay (`php8.4-fpm.service`).** Copy `apparmor/abstractions/wpcaregrid-php-fpm-common` and `apparmor/wpcaregrid-php-fpm-staging-legacy` into `/etc/apparmor.d/` (no-overwrite, `root:root 0644`; note `apparmor.service` loads enforce-mode profiles from that directory at the next start or reload, which is harmless until a unit names the profile). Run `apparmor_parser -Q -K -I /etc/apparmor.d <profile>`. Create the fixtures (`fixtures.py create`, Acceptance step 1). Load in **complain** mode (`apparmor_parser -r -C …`). Only now copy `php8.4-fpm.service.d/90-wpcaregrid-confinement.conf` into `/etc/systemd/system/php8.4-fpm.service.d/`, verify with `systemctl show -p DropInPaths php8.4-fpm.service`, and `systemctl daemon-reload`. Restart `php8.4-fpm.service` in its window, soak in complain mode for at least one full business day of sibling-vhost traffic, review `apparmor="ALLOWED"` records (each is a missing rule or a protected-tree access: any protected-tree access is a STOP), then reload in enforce mode, restart, and run Acceptance for `wpcaregrid-php-fpm-staging-legacy`.

**Stage 2 — staging-next FPM (`php8.5-fpm.service`).** Same sequence with `wpcaregrid-php-fpm-staging-next` and `php8.5-fpm.service.d/90-wpcaregrid-confinement.conf`, inside the staging maintenance gate: record the baseline unit text, complain mode, drop-in, `daemon-reload` (only now), restart, smoke test, review, enforce, restart, smoke test, Acceptance for `wpcaregrid-php-fpm-staging-next`. On a start or smoke failure: Rollback immediately (R1–R3).

**Stage 3 — edge and job peers, and fencing production jobs.** Still before any production secret or route. Each sub-step is its own GO if the host owner prefers, and each follows the same complain-then-enforce sequence (install the profile file, load with `-C`, copy that unit's drop-in only now, `daemon-reload`, restart in its window, review, enforce, restart, Acceptance for the profile):
- *nginx:* `wpcaregrid-nginx` with `nginx.service.d/90-wpcaregrid-confinement.conf`. Record `systemctl cat nginx.service` first (the packaged helper commands run under the profile). Smoke every vhost: public roots must serve; `/.env`, `/storage/`, `/bootstrap/cache/config.php`, `/config/app.php` must not.
- *queue workers and schedulers:* `wpcaregrid-php-cli-staging` with `supervisor.service.d/…`, `wpcaregrid-staging-next-scheduler.service.d/…` and `wpcaregrid-staging-legacy-scheduler.service.d/…` (units that exist; the legacy scheduler unit replaces the www-data cron entry first). Stop the workers through the existing controlled procedure before restarting `supervisor.service` (Supervisor children inherit the profile only at start); confirm both programs `RUNNING` with the new PID and `/proc/<pid>/attr/current` equal to `wpcaregrid-php-cli-staging (enforce)`.
- *no www-data cron:* the legacy `www-data` crontab is removed (`crontab -r -u www-data` after the legacy scheduler unit is running), no `/etc/cron.d` entry runs as `www-data`, no `at` job exists. There is no cron profile and no exact-path attachment: a cron child is an unconfined same-UID shell and is not permitted.
- *fence production jobs:* `systemctl mask wpcaregrid-production-scheduler.timer wpcaregrid-production-scheduler.service` (the names the production policy declares), confirm no `wpcaregrid-production-*` Supervisor program exists (or is `STOPPED` with `autostart=false`) and that the production worker and scheduler fence markers exist. A masked unit cannot be started by anything; this is the fail-closed start policy. Never unmask as part of rollback.

**Stage 4 — pre-production peer gate (production absent).** Run `collect-peers.py` (quiesced: maintenance gate, no deploy) and `verify-acceptance.py ... pre` for `wpcaregrid-php-fpm-staging-legacy`, `wpcaregrid-php-fpm-staging-next`, `wpcaregrid-nginx` and `wpcaregrid-php-cli-staging`. This phase does **not** need the production unit (which may only start after it passes): the production role is excluded, the production unit must have **no** process, and no non-fixture file may exist in the production tree. Every process holding uid/gid/supplementary group 33, and every service master, must map to a permitted class. Any other process is a STOP: Stages 5–6 may not begin, production secrets may not be provisioned and no production route may be opened.

**Stage 5 — production unit, unrouted, then post-start verification.** Only after Stage 4 passes. Copy the production profile, **`wpcaregrid-php-cli-production-deploy`**, the unit and FPM config (`php-fpm/production/*`) to their active paths (the deploy CLI profile is loaded, never attached to a unit; it exists so the root console can run PHP as `www-data` without widening the FPM profile); load the profile in complain mode, `daemon-reload`, start `wpcaregrid-production-php8.4-fpm.service`, exercise it by a local FastCGI request to its own socket only, review ALLOWED records, enforce, restart, and run the **post** phase (`verify-acceptance.py ... post`) for `wpcaregrid-php-fpm-production`, for `wpcaregrid-php-cli-production-deploy` and again for the other four profiles, now with the production role present. The production profile can only be accepted in this phase.

**Stage 6 — remove fixtures; release the production gate.** `fixtures.py remove`, then `fixtures.py status` must report none. Only then may a separate Owner GO provision real production secrets and open the production Nginx route, and that GO requires workstream A's canonical preflight (policy check plus the root observation, including the complete peer inventory, the fenced production jobs and the www-data cron prohibition) to pass, a fresh `collect-peers.py` with no unmapped process, and the evidence from Stages 1–5. The production Nginx route is never changed before this stage.

Never combine stages in one GO. Do not restart any serving FPM service outside its approved window.

## Live acceptance (required; kernel enforcement is shown here, not in source tests)

A denial counts only when the unconfined baseline reached the same target, the confined run was refused with `EACCES`/`EPERM`, a kernel `apparmor="DENIED"` record names the probe profile, the probe pid, an appropriate operation and the target, and the same-UID inventory was complete before and after. Record sanitized output only.

1. **Fixtures.** `python3 "$PKG/acceptance/fixtures.py" create "$PKG/acceptance/matrix.json"` creates canary files (constant non-secret text) with the same owner/group/mode a real secret would have: for example `production/shared/.env` is `root:33 0640`, storage is `33:33 2770`. It refuses before changing anything if any target already holds other content (for example a real `.env`). Required because an AppArmor denial proves nothing where DAC would deny anyway. `status` must list none before Stage 6 ends.
2. **Attribution.** For the master and every worker: `cat /proc/<pid>/attr/current` equals `<profile> (enforce)`.
3. **Fail closed.** With the profile unloaded, starting the new **production unit** must fail; reload afterwards. Not performed on a serving pool.
4. **Mount namespace.** `nsenter -t <MainPID> -m -- ls <other environment path>` shows the path absent or inaccessible (separate from AppArmor).
5. **Unit descriptors.** `collect-peers.py` records every descriptor of every master and worker (root-owned masters included); the verifier requires only expected targets and none under another environment, the control plane, `/home` or `/var/lib/mysql`. Inherited descriptors the unit is not given are never relied upon to be revoked: see below.
6. **Probe run (per profile; six profiles: the three FPM profiles, `wpcaregrid-nginx`, `wpcaregrid-php-cli-staging`, `wpcaregrid-php-cli-production-deploy`).** Take a stable peer inventory first, as root (`python3 "$PKG/acceptance/collect-peers.py" "$PKG/acceptance/matrix.json" > inv-before.json`; it performs two consecutive scans and refuses churn, so quiesce traffic). Pick one www-data **worker** pid (never a root master) of each *other* required role from it (phase `pre`: staging-next, staging-legacy, nginx; phase `post`: also production); job-role processes are inventoried and fd-checked but are not probe targets. Then, for the baseline and again for the confined run, start a fresh sender (from the **published** harness, not the root-only package) and the probe:

   ```bash
   python3 "$PKG/acceptance/derive-probe-profile.py" < /etc/apparmor.d/<profile> > /run/wpcg-probe-profile
   # load once: apparmor_parser -r /run/wpcg-probe-profile  (name <profile>-probe, enforce); UNLOAD it after the run
   # (apparmor_parser -R /run/wpcg-probe-profile): it grants python and, for the deploy profile, production secrets. The
   # verifier refuses any inventory that still shows a process with a probe label.
   systemd-run --collect --unit wpcg-fd-sender -p User=www-data -p PrivateTmp=no \
     /usr/bin/python3 -I -B /usr/local/libexec/wpcaregrid-php-fpm-harness/1.0.3/fd-sender.py "$N" /home/wpcg-fixture/canary
   systemd-run --wait --collect --pipe -p User=www-data -p PrivateTmp=no -p NoNewPrivileges=yes \
     -p StandardInput=file:/home/wpcg-fixture/canary [-p AppArmorProfile=<profile>-probe  # confined run only] \
     /usr/bin/python3 -I -B -c "$(cat "$PKG/acceptance/probe.py")" <baseline|confined> "$(cat "$PKG/acceptance/matrix.json")" \
     <profile> '{"peers":{"<role>":[<worker pid>]},"scm_socket":"/tmp/wpcg-probe-'$N'/scm.sock","abstract":"wpcg-probe-'$N'"}' > <baseline|confined>.json
   # tcp key for the probe's connect checks, from the sender's READY line `READY <path> <abstract> v4=<port> v6=<port|none>`:
   #   "tcp": {"AF_INET": ["127.0.0.1", <v4>], "AF_INET6": ["::1", <v6>]} (omit AF_INET6 when v6=none)
   journalctl -k -o json --boot "$(cat /proc/sys/kernel/random/boot_id | tr -d -)" --since "@$T0" --until "@$T1" > audit.jsonl
   python3 "$PKG/acceptance/collect-peers.py" "$PKG/acceptance/matrix.json" > inv-after.json
   python3 "$PKG/acceptance/verify-acceptance.py" "$PKG/acceptance/matrix.json" <profile> <pre|post> baseline.json confined.json inv-before.json inv-after.json audit.jsonl
   ```

   The derived probe profile is the real profile plus only python exec/library reads and `attr/current`. It does **not** replace testing the real profile (next step). The sender and the baseline probe are unconfined same-UID processes: take both inventories while they are not running. The probe never reads content except exactly-canary-sized files, and never ptrace-attaches to a real peer. Every result carries the pid that made the call (the probe, or its execve child, whose output goes to `/dev/null`) and its own nanosecond time window; the document records the boot id, the probe pid, its kernel start time and lifetime. The verifier accepts a denial only from `journalctl -o json` records of the same boot, inside the probe's lifetime and the call's own window, with a unique audit serial, naming the probe profile, that pid, the exact target and an appropriate operation, each consumed by one check. ptrace is calibrated on a descendant with a really mapped address (`process_vm_readv` returns a byte, never a bare `EFAULT`); for real peers `EFAULT` in the baseline means the kernel permitted the access, while a Yama refusal in the baseline voids that peer check unless the calibration passes. `/proc/<peer>/{environ,cmdline,maps,mem,fd/,fdinfo/,root/,cwd/,exe,ns/mnt,auxv}` each bind to their own exact target (or a ptrace event of their own window); the descriptor transfer reports its stage (connect, recv, read) and passes only with an actual denial errno plus the event for that exact stage (`file_receive` on the canary for recv/read; `connect` on the socket path for connect); `ENOENT`, `EIO`, nothing received or an unrelated event fail. The probe also tests symlink escapes, an abstract-socket connect, and **actually reads the inherited descriptor on fd 0** (`StandardInput=file:` above), reporting whether the kernel revoked it.
7a. **Deploy CLI, real profile.** With the real profile (not the probe profile) run, as the helper does, `runuser --user www-data --group www-data -- /usr/bin/aa-exec -p wpcaregrid-php-cli-production-deploy -- /usr/bin/php8.4 -r 'echo getcwd();'` from the active release: it must run, `/proc/<pid>/attr/current` (read from a second root shell while it runs) must be `wpcaregrid-php-cli-production-deploy (enforce)`, the peer inventory taken while it runs must list it as the permitted transient class (confirm on the host that `runuser` does not move the child out of the root-console `session-N.scope`: if it does, the class fails closed), and its release `bootstrap/cache` writes (`package:discover`, `config:cache`) must succeed. A direct `exec` of `/usr/bin/dash` or `/usr/bin/php8.5` through `aa-exec` may fail at the transition (missing `m`/`r` on the binary) rather than on a `deny x` rule, so it is not the proof of the exec denials. The proof is **nested exec from inside PHP**, each of which must fail with an exec denial in the audit log under the deploy profile: `php8.4 -r 'var_dump(proc_open(["/usr/bin/id"], [], $p));'`, `php8.4 -r 'pcntl_exec("/usr/bin/dash", ["-c","id"]);'`, `php8.4 -r 'system("id");'` and a `curl`/`python3` exec. Also `php8.4 -r` reading a staging `.env` and the control-plane fixture must fail with their audit records, and **every** attempt to open TCP (`stream_socket_client('tcp://127.0.0.1:…')`, `fsockopen('::1', …)`, `socket_create` for IPv4/IPv6), a UDP socket, a unix datagram socket, a unix connect to any path other than the one MySQL socket, or a `bind` must fail with an audit record; the connection to the one MySQL socket must work. Complain mode first: the PHP extension set and `/etc/php/8.4/cli` loads are assumptions. The python probe (step 6) proves the same file, network and process rules on the derived probe profile; step 7a is the only place the real `php8.4` transition is exercised.
7. **Original-profile exec denial.** The probe profile grants python, so `exec-python` is not a probe check. Run `systemd-run --wait --collect -p User=www-data -p AppArmorProfile=wpcaregrid-php-fpm-production /usr/bin/python3 --version` (and the equivalent for the other profiles that deny it): it must fail to exec, and the audit log must show `operation="exec"` `profile="wpcaregrid-php-fpm-production"` DENIED for `/usr/bin/python3`.
8. **Kernel features and audit.** Record the AppArmor feature files; if `ptrace`, `signal` or unix mediation is absent the corresponding claims are void and the stage stops. `DENIED` records for the probe pid with no matching check fail the run as unexplained.
9. **Application smoke.** Existing deployment smoke and health checks unchanged from the recorded baseline.

**Inherited descriptors.** Path rules are evaluated when a file is **opened** (and when a descriptor is received over a socket). A descriptor already open keeps working if the path would now be denied, so a confined process that inherits an open descriptor to another environment's file can still read it. The assumption to verify, **never rely on exec-time revocation**: the kernel may revalidate or close descriptors a new profile does not permit at an `execve` transition, but this repository cannot demonstrate it, and the behavior does not cover descriptors a process opened before a profile *reload* of a running service (only a restart applies a profile). Design consequences:

- The units pass no extra descriptors: `StandardInput=null`, no `Sockets=`/`ListenStream=`/`OpenFile=`, `FileDescriptorStoreMax=0`, no `PassFileDescriptorsToExec`, no credentials. The profile is selected before the first `execve`, so master and workers start confined.
- Acceptance reads fd 0 in both runs and records the outcome; whichever it is, safety rests on the unit descriptor inventory (step 5) showing nothing foreign. Inspect `/proc/<pid>/fd` of the master and every worker; any descriptor outside the allowed set fails the run.
- `SCM_RIGHTS` from an unconfined same-UID peer reading as a confined process is a **failure** unless explicitly acknowledged with `--ack-fd-transfer-bypass` in a reviewed record; the abstract-socket and `/run/php` path denials are what keep a rendezvous from existing.

## Rollback

Rollback uses only reversible, hash-checked operations and never touches databases or application files. **Invariant I governs the order: production is fenced before any same-UID peer is returned to unconfined.** Restoring any peer (an FPM pool, nginx, the queue workers or a scheduler) to unconfined while any production secret-bearing path is readable by uid/gid 33 would reopen the exposure. The same continuity applies at every stage: a rollback in Stage 1, 2 or 3 either finds production not yet provisioned (recorded) or runs R1–R2 first. The order is encoded, and fault-tested, in `acceptance/rollback-order.py`.

- **R1 — fence production traffic, service and jobs.** Close the production route (Nginx maintenance gate, existing marker procedure), stop the production workers and scheduler under their fence markers, then `systemctl stop wpcaregrid-production-php8.4-fpm.service`, and confirm no production deploy CLI (`aa-exec` `php8.4`) is running, detected by the process label in `/proc/<pid>/attr/current`, never by name (the order aborts in R1, before any change, while one exists: it reads production secrets as `www-data`, and removing its profile would leave it unconfined). Lock the root-console helper out for the whole rollback so none starts meanwhile; the order re-checks immediately before R4. The production scheduler units **stay masked** and no production Supervisor program is started or autostarted: never unmask during rollback (the order aborts if a production job unit is not masked and inactive). Record states. If production has never been provisioned or routed, record that and continue.
- **R2 — fence production secrets: every path, not only `shared/.env` and `shared/storage`.** `python3 "$PKG/acceptance/fence-production.py" fence "$PKG/acceptance/matrix.json" --receipt <file>` makes every path under `/var/www/wpcaregrid-production`, `/var/lib/wpcaregrid-deploy/production` and `/var/log/wpcaregrid-production` unreadable to `www-data` (owner root, file `0600`, directory `0700`, ACL xattrs removed) except public web roots (`releases/*/public`) and the traversal-only directories nginx must pass. That includes each release's `bootstrap/cache/config.php` (the config cache carries the same secrets), release `.env` files, production logs, state markers, storage and backups. Prior owner/mode/ACL of every path is recorded in the receipt before the change, so an interrupted run stays reversible and a re-run completes it. `fence-production.py status` must exit 0 (no path readable, writable or searchable by uid/gid 33); it never follows symlinks and never reads content. Fixtures only: `fixtures.py remove`.
- **R3 — only now restore peers, one at a time, newest stage first**: `jobs-legacy-scheduler`, `jobs-scheduler`, `jobs-supervisor`, `nginx` (Stage 3), then `staging-next` (Stage 2), then `staging-legacy` (Stage 1). For each: re-run `fence-production.py status` (must be clean, production not routed or running, production jobs masked) immediately before removing that peer's drop-in, `daemon-reload`, restart that unit, confirm `/proc/<pid>/attr/current` is `unconfined` for its processes and its smoke test passes, then re-run the status again; a path re-exposed by anything (for example a deploy re-creating a world-readable `config.php`) stops the remaining peers. Removing a drop-in or unloading a profile does **not** change a running process; the restart reverts it.
- **R4 — remove artifacts.** `apparmor_parser -R` each profile (the deploy CLI profile too; it has no service to restart), delete only files whose SHA-256 matches `SHA256SUMS`, `daemon-reload`. Production stays fenced (R1–R2, jobs masked) until a new GO re-runs the cutover (`fence-production.py restore` is part of that GO, not of rollback).
- **Partial rollback.** Reverting any single peer requires R1–R2 first, because any one unconfined peer already violates Invariant I.
- **Failed install (Stage 0/1):** delete only files whose hash matches; leave any non-matching file untouched and report it.

Stop conditions: a file or label that differs from the recorded baseline, a unit that will not restart, a production path still readable after R2, a production job unit that is no longer masked, or a failed smoke test. Keep the maintenance gate, do not retry blindly, and escalate with the recorded evidence.

## What the next engineer must know

- Changes to installed profiles always need a new artifact version directory (`1.0.3`, …), a new `SHA256SUMS`, new compiled hashes in a new contract version, a new test run and a new GO. Do not edit `1.0.3` in place after review.
- `acceptance/matrix.json` is the single source for the model test, the live probe, the verifier and the fixture manifest; update it with every access change.
- `scripts/tests/php-fpm-confinement-test.py` is wired into CI; the real-parser compile runs there (`apparmor_parser` 4.0.1 from Ubuntu 24.04 compiles every profile and probe profile; locally set `APPARMOR_PARSER_BIN` and `APPARMOR_PARSER_BASE`).
